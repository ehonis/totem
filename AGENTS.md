# AGENTS.md — Totem

Operating manual for any human or AI agent working on this repository. Read it first: it
explains how the system fits together, where things live, the rules the code depends on, and
how to run and test it.

If `AGENTS.local.md` exists, read it too: it holds the owner's deployment-specific notes.
It is gitignored and never part of the public repository.

> **Keep this file accurate.** A change that adds a feature, alters behaviour, adds a setting,
> swaps a backend or changes how Totem is run updates this file in the same change. If you
> learn a gotcha the hard way, add it to "Gotchas". Deployment-specific facts (hostnames,
> accounts, personal workflows) belong in `AGENTS.local.md`, not here.

## 1. What this is

Totem is a self-hosted, single-owner personal assistant. One Node process (`bridge.mjs`)
serves a React dashboard and an HTTP API, runs scheduled jobs, and answers requests by spawning
whichever agent CLI is configured (Codex, Claude Code, OpenCode or Cursor). The agent acts on the
owner's local data (tasks, goals, habits, lists, a Markdown notes repo) and on connected services
(Google Calendar, GitHub, Strava, WHOOP, Plaud, MCP servers).

A fresh install is a blank canvas: no account until the owner creates one, no AI until one is
set up, no scheduled jobs running, no personal prompts or data.

Docs, by job:
- `README.md` — what it is, features, quick start.
- `docs/self-hosting.md` — sign-in, settings vs env, Docker, systemd, data and backups.
- `SETUP.md` — the out-of-browser steps: phone shortcut, Tailscale, MCP servers, jobs.
- `mobile/AGENTS.md` — the iPhone app: how it mirrors the web, building and shipping it.
- `docs/*.md` — one file per subsystem (see the map below).
- `TOTEM-OVERVIEW.md` — the design write-up.
- This file — the mental model and the rules for changing the code.

## 2. Request flow

```
Phone shortcut / mobile client        Web dashboard (React, served by the bridge)
  POST /ask, /ask-text                  /api/*  (session cookie or bearer)
  Authorization: Bearer <BRIDGE_SECRET>
                 │                                 │
                 └──────────────► bridge.mjs ◄─────┘   port BRIDGE_PORT (8787)
                                    │
     direct reads/writes: tasks, goals, lists, habits, calendar, notes, usage
                                    │
                            runAgent(): spawn the selected agent CLI
                              codex exec | claude -p | opencode run | cursor-agent -p
                                    └─ mcp-gateway.mjs → Totem tools + manifest MCP servers
```

The dashboard reads data directly; the agent is used for chat, phone requests, jobs and
open-ended work. The default provider and model come from Settings → Providers (stored in
`data/provider-config.json`); `AGENT_BACKEND`/`AGENT_MODEL` are only first-run fallbacks.

| Server | `bridge.mjs` | HTTP routes, prompts, agent backends, scheduler tick, OAuth clients for Calendar. Large on purpose; new subsystems go in their own directory and are composed here. |
| Sign-in | `auth/owner.mjs`, `auth/http.mjs`, `web/src/components/AuthGate.tsx` | One owner. First run prints a one-time `/setup?token=…` link; scrypt password in `data/auth.json` (0600); signed httpOnly `SameSite=Lax` cookies, `Secure` behind https; change password bumps a session version. `BRIDGE_SECRET` bearer always signs in, but never approves anything on its own (next row). | Approval code | `auth/approval-code.mjs`, `auth/approval-routes.mjs`, `auth/approval-code-cli.mjs`, `web/src/approvalCode.ts`, `mobile/src/lib/approvalCode.ts` | A second credential that stops a caller holding only the bearer, **not** an agent that can write `data/` or the checkout (`docs/self-hosting.md` → What remains open). The routes in `APPROVAL_ROUTES` (inbox resolve and release, MCP session approve, Messages send, totem proposal, chat tool approvals, recommendation decisions and outcomes, the owner's away-span writes; a route may be a `pattern` and has its own method; a `POST /api/recs` without a session or the code records as an agent, so the 30-day declined hold applies) are matched on `normalizeApiPath` (slashes and dot segments folded, the same path every handler sees) and refuse the bearer alone. High-risk decisions (send, run, open a prompt, file an issue, activate a session, accept an agent's `away` proposal, any unknown kind) need the code once set; low-risk ones (local task, calendar, goal metric, a chat's tool approval, a rec's decision or outcome, any deny) take a signed-in session. Sent as `x-totem-approval-code` from localStorage (web) or the keychain (app, bound to its server). Only a salted HMAC-SHA256 is stored (`data/approval-code.json`, 0600; the code is 100 random bits, so no slow hash; a pre-merge scrypt record is upgraded on its first correct code), with the install decision (`fresh`/`existing`) and armed date; `data/auth.json` (`approvalCode`) keeps a second copy and the record id. The trusted record is held in memory and compared on every check and at boot: a replaced, planted or downgraded file reads as `tampered`, refuses high-risk approvals, notifies and logs until the owner sets a new code. The record id is an unkeyed hash, so a consistent rewrite of both files plus a restart is **not** detected. Set after re-entering the password (`POST /api/auth/approval-code`) or by `npm run approval-code` (TTY plus password whenever an owner exists; paths from the checkout's `.env`, never the caller's environment; loaded at the next start). Wrong codes are counted per client and per credential and turn into 429s; a correct code is always verified at once (no queue) and never refused for a flood. States: `armed`, `missing`, `tampered`, `legacy` (existing install, none set: session alone approves, owner told once), `unset` (fresh, none set). `docs/self-hosting.md` → The approval code. |

## 4. Defaults and settings

- **Everything optional is off on a fresh install.** Every seeded job is created disabled except
  the two local task-board housekeeping jobs, which only apply archive/retention preferences.
  `jobs/defaults.test.mjs` enforces this. A job whose code is removed goes in the job store's
  `retiredIds`, so a saved entry is dropped rather than left to fail or re-seeded.
- **Existing installs keep their behaviour.** When a default changes, the new value applies to
  fresh installs only. Detect an existing install from data that predates the process
  (`EXISTING_INSTALL` in `bridge.mjs`, rows already in a table) and record the decision once.
  `data/jobs.json`, `data/provider-config.json` and seeded skills are never re-seeded over.
- **Env wins over dashboard settings**, except `AGENT_BACKEND`/`AGENT_MODEL` and the
  `*_ENABLED`/`*_TIME` job seeds, which only apply before the stored config exists.
- **Sibling apps are optional.** The Bushido goal toggle appears only with `BUSHIDO_URL`.
- **Who the owner is** comes from `OWNER_NAME`; prompts otherwise say "the owner".
- `.env.example` documents every variable.

## 5. Rules the code depends on

- **Direct reads, agent writes.** Dashboard data comes from the bridge reading its own stores
  or APIs, never from an agent round-trip.
- **Confirm-only for anything inferred.** Journal and meeting ingests, MCP-proposed commands and
  agent runs are staged in the inbox (accepting a `prompt` opens it as a new T3 Code thread,
  `T3_CODE_URL/new?prompt=`; Totem no longer runs it). Prepare the finished work before asking, so accepting is
  one call with nothing left to interpret.
- **Channels.** A request carries a channel. `http` (phone) replies are plain text with no
  Markdown and must not ask follow-up questions (they emit one `NEED_INPUT:` line instead);
  `web` may use Markdown and ask. Pick the channel deliberately when adding a front door.
- **Date grounding.** Every prompt carries the local date, a 14-day date table (away days
  marked), the owner's current and coming away spans, and an instruction to verify weekday/date
  pairs (`away/grounding.mjs`, through `temporalContext()`).
- **Memory is not the task list.** Completed actions and facts go to the notes repo; future
  obligations go to tasks or the calendar.
- **Tasks are local.** Nothing shares a task out: `syncTarget` takes only `local`
  (`assertSyncTarget`), and no connector owns completion, so a task with a GitHub issue link
  or a link left by the retired sheet sync completes and reopens here like any other, and a
  repeating one rolls its next occurrence (`rollsOnCompletion` in the shared `board.ts` must
  keep agreeing with `todos/service.mjs`, or the clients offer an Undo that duplicates it).
- **Nothing scheduled completes or postpones a goal.** `postponed_count` records the owner's
  decisions; automation reports and asks.
- **An unreadable metric is not zero.** A connector-fed goal metric that cannot be read is
  `available:false` and drops out of the progress mean.
- **Route every agent spawn through `runAgent`**, and give slow callers their own `timeoutMs`.
- **Audit once.** Domain services write the action log after a committed mutation; adapters do
  not log the same write again.

## 6. Running, building, testing

```sh
pnpm install                # root deps, then the dashboard's (postinstall)
pnpm start                  # builds web/dist if missing, runs the bridge with .env if present
pnpm run build              # rebuild the dashboard after changing web/
pnpm test                   # bridge test suite (node --test)
cd web && pnpm test         # dashboard unit + vitest suites
cd web && pnpm run build    # typecheck (tsc --noEmit) + vite build, as CI does
```

- **pnpm, not npm: never run `npm install` or `npm ci` at the root or in `web/`.**
  Each has its own `pnpm-lock.yaml` and a settings-only `pnpm-workspace.yaml` (`nodeLinker: hoisted`,
  so `node_modules` is laid out as npm laid it out; `onlyBuiltDependencies` lists the packages whose
  install scripts may run). npm ignores those lockfiles and writes its own tree. pnpm is pinned in
  `package.json` (`packageManager`) and comes from Corepack (`corepack enable pnpm`; Node 25+ needs
  `npm i -g corepack` first). The root scripts call it through `scripts/pnpm.mjs`, which falls back
  to `corepack pnpm` when `pnpm` is not on PATH.
  **`mobile/` and `desktop/` stay on npm** (`package-lock.json`, `npm ci`). EAS builds the iPhone
  app with whatever lockfile it finds, and that build is not provably the same under pnpm. The
  desktop install is three packages (no memory to save), and any change under `desktop/` makes
  CI build and the release tooling publish a signed update to every installed desktop app.

The systemd user unit template is `assistant-bridge.service` (`pnpm run service:restart`,
`service:logs`, …). Docker: `docker compose up -d --build`. CI (`.github/workflows/ci.yml`)
runs the dashboard build and tests, and the bridge test suite with `pnpm install --frozen-lockfile --ignore-scripts`. In a private
repository CI and the deploy's iPhone job run on a self-hosted runner labelled `box`; a public copy uses GitHub's
hosted runner (`github.event.repository.private` picks).

Useful focused commands:
- `node --test todos/*.test.mjs todos/connectors/*.test.mjs` — tasks, migrations, connectors
- `node --test goals/*.test.mjs`, `node goals/cli.mjs list|review`
- `node todos/cli.mjs backup|export|restore`
- `node mcp-gateway.mjs --status`
- `TERMINAL_E2E=1 node --test terminal/e2e.test.mjs` — drives a real shell
- `curl -s localhost:8787/health`

### Adding or syncing MCP servers
1. Prefer Settings → Connections. "Import from Cursor" seeds the manifest from an existing Cursor
   config.
2. The manifest is `data/mcp-manifest.json` (gitignored; env values can hold tokens). Local servers
   are `{ "transport": "stdio", "command", "args", "env" }`, remote ones
   `{ "transport": "http", "url" }`.
3. Sync writes each provider's native config (backing up what it replaces) and only touches
   servers whose ids are in the manifest.
4. Remote OAuth servers still need each CLI's own login after sync.

### Database migrations
Ordered modules in `todos/migrations/`, recorded by version in `schema_migrations`; each runs in
its own transaction. A migration may declare `foreignKeysOff` (the runner turns foreign keys off
around it and runs `foreign_key_check` before commit — required for any table rebuild, or the
DROP fires every `ON DELETE CASCADE`) and `backupBefore` (an existing database is copied with
`VACUUM INTO` first). Test a migration against a fixture built by the earlier migrations, check
row counts, ids and foreign keys, and run it twice.

## 7. Gotchas

- **Never hand-draw an icon.** The dashboard uses Heroicons (`web/src/icons.tsx`) and Tabler for
  what Heroicons lacks. Confirm a name exists
  (`ls node_modules/@tabler/icons-react/dist/esm/icons | grep -i <term>`) and import it deep and
  per-icon as a default export so the package tree-shakes. See `web/src/goals/sportIcons.tsx`.
- **Entry checks compare real paths.** Node resolves symlinks in `import.meta.url` but not in
  `process.argv[1]`, so a script launched through a symlinked checkout must use
  `isEntry(import.meta.url)` from `scripts/is-entry.mjs`. Otherwise it loads, decides it was
  imported, and exits 0 silently (an MCP client reports the gateway as "connection closed").
- **The bridge has dependencies.** After pulling changes to `package.json`, run `pnpm install` at
  the root or the service will not boot. `node-pty` is optional (it needs a C++ toolchain) and
  only the web terminal uses it.
- **A chat never edits the checkout Totem runs from, and never vets its own guardrails.** A change to Totem goes through `change_start`/`change_finish` (`dev/change.mjs`), which run the live checkout's copy of the checks, not the worktree's. Paths that guard the flow are refused rather than flagged, because pushing a branch already runs its `.github/workflows/` on the self-hosted runner and the owner merges from a card. Keep any new guardrail, auth, approval or rule-enforcing file in `PROTECTED`/`PROTECTED_FILES` (or its identifiers in `GUARDED_LINE`), compare paths through `foldPath` (the deploy host's filesystem is case-insensitive), and push only the commit `finish` built from the tree it checked, never `HEAD`: the agent's own history and the checks (which run the change's code) are untrusted. Never give the flow a merge, a force-push or a branch outside `totem-change/*`. The deny rules only cover Claude's file tools; a shell can still write anywhere, so the tree check in `finish` is the boundary for every backend. Never trust a field of `data/changes.json` without checking it against git or GitHub (an agent's shell can edit it), never read git output through a cap (a cut-off list passes whatever was cut), and scan whole files at the pushed tree rather than diff lines (a changed line `++ x` prints as `+++ x`, the shape of a header). Nothing on `main` enforces "no merge" yet: that needs branch protection, which is the owner's call.
- **A worktree's `node_modules` symlink must stay ignored.** A trailing slash (`node_modules/`) matches only a directory, so a symlinked `node_modules` was once committed; the live checkout's real directory then read as a deletion, and the deploy refused every merge as "uncommitted changes". Ignore it as `node_modules`, without the slash.
- **A provider's config holds the gateway, never the manifest's servers.** The gateway reads the manifest itself, so adding, toggling, removing or re-syncing a connection writes `providerManifest()` (the gateway in gateway mode, nothing when off) to each provider. Codex's managed block is rewritten whole, so writing the manifest there once replaced the gateway and left every Codex chat without Totem's tools (it fell back on a stale ChatGPT app). `providers/mcp-sync.test.mjs` drives each route and checks Codex's `config.toml`.
- **systemd's PATH is not your shell's.** The bridge spawns agent CLIs by name; a unit without
  `~/.local/bin` and the node bin dir on `Environment=PATH` starts fine and then fails every
  request with "command not found".
- **MCP sync is config, not shared OAuth.** Each CLI keeps its own MCP tokens. Browser redirects
  to `127.0.0.1` must complete on the machine that owns the CLI's token store; the Connections
  tab has a callback-replay helper for redirects that landed elsewhere.
- **A retired model does not fail loudly.** Codex answers an unsupported model with a 400 and no
  assistant message, and exits 0. Model choices go through `resolveModelChoice()` against the
  live catalog, and a run with no assistant message throws.
- **Claude's model list is written by hand.** Claude Code has no model-list command, so a new
  Claude model appears in Totem's pickers only once it is added to `MODEL_SEEDS` in `bridge.mjs`
  (with a `note`), however recent the CLI is. Retire a model by moving its id to
  `CLAUDE_SUCCESSORS`, never by just deleting it, or a saved choice falls back to Opus.
- **`AGENT_TIMEOUT_MS` is a phone-request budget.** Long jobs pass their own `timeoutMs` to
  `runAgent`; Cursor answers a killed run with prose rather than an error, so treat a non-answer
  as a failure.
- **A redaction pattern must run in linear time.** `chat/redact.mjs` sees every command's output on its way to a tool card or an error, and a name pattern like `[\w-]*token[\w-]*` retried at every position took 23 s on 100,000 letters. Start a name only at the start of its run (a lookbehind), bound its length, keep each lookahead inside the run's own characters, and keep `chat/redact.test.mjs`'s 100k timing test passing.
- **A web terminal counts keystrokes, not commands.** When reconstructing submitted lines, lose
  the label rather than store a secret; the password guard latches once armed. Only the e2e test
  against a real shell catches regressions there.
- **WHOOP refresh tokens rotate, so one process holds them, and it is Bushido.** Every refresh
  voids the old refresh token, so two holders of one grant refresh each other's tokens away and
  one stops working without a sound. Totem never holds WHOOP (or Strava) credentials: it reads
  WHOOP through `whoop/remote.mjs` (`POST /api/whoop/owner` on Bushido), and the sibling apps
  read WHOOP from Bushido, not from Totem. Never add a WHOOP OAuth flow or token file here.
- **Strava's `start_date_local` is not an instant**: it is local wall-clock time with a `Z`
  appended. A missing scope is a 401 carrying `<scope>_permission missing`.
- **Web Push `Topic` must be ≤32 URL-safe base64 characters** or Apple drops the push with
  `400 BadWebPushTopic`.
- **Every push goes through `notifier.deliver`.** That is where the dedupe gate runs; a second
  way out (a webhook, a direct APNs call) is a second place repeats get through, so the jobs
  store's webhook is skipped when `deliver` returns `suppressed`. A fact that stays true for days
  needs its own `dedupeKey` and `dedupeUntil`: the derived key ends in the plan date, which is how
  a spent Cursor window pushed three times a day for eleven days. A shared model name is never a
  match on its own (`storyScore`): a launch and its outage, a release and its delay, or GPT-6.1
  and GPT-6.2, are two stories, and a false match deletes news without a trace. The event check
  is one-sided (`storyScore(later, earlier)`): a follow-up names the event it follows. Text-keyed repeats are opt-in per
  category (`textDedupe`), because "stopped reporting" after "back" is news.
- **Recording needs HTTPS.** `getUserMedia` is unavailable on plain-http origins other than
  localhost. Never pass a `timeslice` to `MediaRecorder.start()`; Safari's fragments do not
  concatenate reliably.
- **Build a date table from day keys, never from an instant plus 24 hours.** On the night
  clocks spring forward, "now + 24 h" lands two local days later, and the prompt's 14-day table
  once skipped a Sunday that way. Resolve today once (`todayKey(now, tz)` in
  `goals/periods.mjs`) and step with `addDays`; format a key as a calendar date, not an instant.
- **Journal entries are files, not rows**, so the task-database export format does not change.
- **The task export format is versioned** (`formatVersion` in `todos/db.mjs`); a restore refuses
  an older format rather than restoring with tables silently missing. The one exception is a
  table marked `since` on `TABLES`: an export older than that version was taken before the
  table existed, so it restores empty (format 3 restores into format 4 with no `recs`).
- **Quota plan names do not imply equal capacity.** A Claude Team seat may report a Max quota tier. Proxy accounts retain that tier's numeric `planSize` separately from the plan label. Inferred refills retain the raw percentage and reset as `beforeRefill`, so graph history can reconstruct the reset without rewriting an earlier lockout. Optional active history recording backs off for ten minutes when its route or scope is unavailable, then retries so adding support works without restarting Totem.
- **The CLIProxy management key is the proxy's root.** The full key can download every login's refresh token and send a login's token to any URL through `/requests/api-call`, and every agent on the host can read whatever Totem stores. Give Totem a scoped key (`management.scoped-keys` in the CLIProxyAPI fork: a route allow-list, `api-call` limited to the vendor usage and reset URLs, no download). Inside Totem, never build an upstream URL, header or auth index from a request: `client.upstream` takes only `UPSTREAM_ALLOWED` URLs, and the passive headers are post-request readings, so prefer them; every active read spends the vendor's rate limit on that login. A management 401 blocks the refused configuration for 30 minutes, cleared by a settings save or Retry; only 401 responses matching both the current configuration and retry generation may arm the guard. Successful replies never clear it, so late replies cannot undo recovery or unblock a newer refusal. Other 403s retain their scrubbed reason instead of telling the owner to replace a valid key.
- **Claude quota polling uses Claude Code's credentials.** `ai-usage/providers/claude.mjs`
  refreshes the stored Claude Code login with the client id built into Claude Code and writes the
  rotated token back to wherever it read it: the credentials file on Linux, or on macOS the
  `Claude Code-credentials` login-Keychain item (`ai-usage/keychain.mjs`; default home only, the
  Keychain is only unlocked in the desktop session, and values go to `security` on stdin, never
  argv). Cursor reads `cursor-access-token` the same way on macOS. Cursor polling calls Cursor's private,
  undocumented usage endpoint. Both are off on fresh installs and recorded once in
  `data/ai-usage.json` (`ensureUsageOptIns`); a poller added later inherits the recorded
  decision rather than re-judging whether the install is new.
- **Never write a Keychain secret through `security`'s `-w` prompt.** It reads at most 128
  characters and stores the truncated value with exit 0; it destroyed the Mac's Claude login on
  the first token refresh. `ai-usage/keychain.mjs` feeds `add-generic-password -X <hex>` to
  `security -i` on stdin (a line over ~4 KB fails there too, so long values are refused before
  the refresh token is spent) and reads the item back to confirm.
- **Agents can read what the bridge's user can read.** Every agent CLI runs as the same user as
  Totem, in `AGENT_CWD` (default: the checkout), so `data/auth.json` (password hash and the key
  that signs session cookies), `.env` (`BRIDGE_SECRET`), stored API keys and `secrets/` are
  readable in principle. What each backend does about it:
  - **Claude Code**: Totem passes `--disallowedTools` deny rules for Read/Edit/Write on those
    paths (`claudeSecretDenyRules`). Verified to block the Read tool. It does not stop a
    shell command (`cat`) if Bash is allowed, which it is in a chat on Full access
    (`bypassPermissions`), or by the account's own settings or launch args.
  - **Codex**: `--sandbox workspace-write` (the default) and `read-only` restrict writes and
    network, not reads; there is no per-path read deny.
  - **Cursor** (`--force`) and **OpenCode**: no per-path deny switch; full user access.
  The only hard boundary is running Totem's data under a different user than the agents, or
  `AGENT_CWD` plus filesystem permissions that keep the agent user out of `data/`. Treat an
  agent as holding the owner's authority, which `BRIDGE_SECRET` in `.env` already implies.
  The approval code narrows one thing: a caller holding **only** the bearer cannot approve.
  It does not stop an agent that writes `data/` or the checkout. Replacing the hash or
  editing the latch is detected (it reads as `tampered`, refuses approvals and notifies), but
  an agent can still rewrite both copies consistently and restart Totem (its own code is then
  armed, unnoticed), delete both copies and forge the rest, forge a session cookie from
  `data/auth.json` (enough for low-risk approvals, and for all of them on `legacy`), edit
  `bridge.mjs` or `web/dist`, create or edit a job with any prompt, use the web terminal,
  use the Gmail/Drive tokens or Messages directly, or read the code from a browser profile on
  a machine it shares. Anything an agent can read (`data/notifications.json`,
  `data/approvals.json`) is no proof, which is why the MCP session's 6-digit code only counts
  on `legacy`. `docs/self-hosting.md` → What remains open keeps the list.
- **A chat run is not its HTTP request.** Closing the browser only detaches a viewer; the agent
  keeps going and the reply is saved. Do not kill a run on `req.on('close')`. A message is not
  safe until the bridge sends `start`; `web/src/chat/store.ts` keeps an outbox in localStorage
  for sends that never reached it.
- **A chat turn starts in `startChatTurn`, whoever starts it.** The composer's `POST /api/chat` and the queue's drain (`drainChatQueue`, on every run's end) share it, and a run's `outcome` (set before `done`) is what decides whether the queue moves on or holds. A new way to start or end a chat run that skips either leaves queued messages waiting for ever, or starts them after a stop.
- **A downstream gets a deadline to connect, never to answer a call.** The gateway times `initialize`, `notifications/initialized` and each `tools/list` page (30 s, 15 s per page, 45 s per server overall; `DEFAULT_TIMEOUTS` in `mcp-gateway.mjs`), caps listing at 50 pages and stops on a repeated cursor. A server that misses its deadline is closed (its whole process tree killed, its HTTP requests aborted) and shows in `--status` and `totem_list_connections` as `{ ok:false, timedOut:true, phase, error }`. Before this, one server that never answered `initialize` kept the gateway from serving anything, built-ins included. `tools/call` stays untimed on purpose: `ask_questions`, totems and long manifest tools legitimately take minutes or hours (next gotcha). An OAuth token refresh is never cut short by those deadlines or by `close()` either: the authorization server may already have rotated the refresh token, so the refresh runs to the end on its own 60 s timeout and saves the result, and the gateway waits for it before exiting (`settleRefreshes`). The gateway answers the runtime's `initialize` at once; `tools/list` waits for the connects, so every runtime still sees one complete list.
- **A question can wait for hours, so nothing on its path may time out.** `ask_questions` answers as an SSE stream with a comment every 15 s (Node's fetch, which the gateway uses, drops a body that stays silent for five minutes), each CLI is told a day-long tool timeout (Claude's per-server `timeout`, Codex's `tool_timeout_sec`, which defaults to 60 s), and the run's clock is held while it waits (`holdableTimeout`). A new spawn path that times out an agent must take `holds` too.
- **Offering the browser must stay free.** Every chat run is offered it, so `grantBrowserAccess` only mints a token and `/agent-mcp`'s `initialize`/`tools/list` answer from static descriptors; Chromium starts on the first `preview_*` call that needs a page. Anything added to the grant or the handshake that touches Playwright launches a browser on every chat turn (`chat/reach.test.mjs` checks the launch count). Watching is free too: `watch` returns null for a chat with no browser, and the panel's socket never creates a session.
- **A headless browser must not say so.** Playwright's headless shell, and new headless Chrome left alone, put "HeadlessChrome" in the user agent, and Cloudflare's check held LinkedIn's sign-in on "Just a moment..." for good. `browser/pick.mjs` prefers a full Chrome or Chromium, and every chat and `readPage` context takes `contextOptions()` (the browser's own user agent minus "Headless", a real screen size). A new context made with bare `newContext()` brings the tell back; `renderPage` alone may, since it loads nothing from the web.
- **The owner's input to a chat's browser is an approval route.** The run that opened the browser holds the bearer, and could otherwise click "Allow" or "Sign in" on what it handed the owner. A new way to send input (another socket, a mobile path) asks what `POST /api/chat/browser/input` asks in `APPROVAL_ROUTES`; `auth/approval-bridge.test.mjs` checks the socket against the real bridge.
- **Killing an agent CLI does not kill its tools.** Cursor runs each shell command in its own session, so a SIGKILLed `cursor-agent` leaves the command running under init. And the CLI on `PATH` may only be a launcher: npm's `codex` is a Node script that starts the native binary with inherited stdio, and SIGKILL cannot be forwarded, so killing the launcher left codex running with the run's pipes open (the chat stuck on "streaming", Stop doing nothing). Agent CLIs spawn in their own process group (`AGENT_SPAWN`, `trackAgent`), and Stop, steering and timeouts go through `killTree` (`scripts/kill-tree.mjs`), which kills the group plus the tree read from `/proc` (or `ps` on macOS) before killing. Tracked agents are killed when the bridge gets SIGTERM/SIGINT, since they no longer share its group.
- **A Codex turn can fail after it has started talking.** `codex exec --json` exits 0 and ends a failed turn with `turn.failed` (a usage limit arrives as `429 Too Many Requests`), often after a commentary message ("I'll check…"). That is a failed reply, not a finished one (`turnFailed` in `spawnCodexStream`). `error` events alone are not a verdict: codex also uses them for retries it recovers from ("Reconnecting... 2/5").
- **A sub-agent's events are not the reply's.** Claude Code streams a sub-agent's text, tool calls and prompt with `parent_tool_use_id` set. Treated as top-level, they leak into the reply's text and tool list and throw off the steering echo count, so `spawnClaudeStream` routes them to `onAgent` before anything else. A background Agent call's tool_result only means "launched"; it finishes on `task_notification`.
- **A chart page is served as a page only under `VISUAL_CSP`.** It is agent-written HTML, so it never gets Totem's origin: no `allow-same-origin` on the frame or in the header's `sandbox` (`servedHeaders` in `chat/uploads.mjs`; every other inline upload but a PDF gets a plain `sandbox` too, so an SVG never runs as Totem). Only uploads saved with `visual: true` (from `storeVisual`) are served inline as HTML; keep the owner's own HTML uploads a download, and never pass `visual` through from a request. CSP does not stop a page navigating itself, so it is not an egress seal: `renderPage` answers every navigation with a 204, the dashboard frame closes on a second load and the app's `BridgeWebView` on any top-level navigation after its first (`bridgeNavigation`). That WebView keeps `originWhitelist={['*']}`: with react-native-webview's default, a URL outside the list goes straight to `Linking.openURL` without reaching the guard. Agent-written HTML is scanned on the bridge's one thread, so bound every attribute run in a regex (`[^>]{0,512}`). A new tool on `/agent-mcp` goes in `agentMcpTools` (`bridge.mjs`), which feeds both `tools/list` and Codex's approvals; the gateway's `browser` filter (`mcp-gateway.mjs`) must pass its name too, or Cursor and OpenCode never see it. A tool result for Codex carries no `structuredContent`, which Codex sends to the model in place of `content`, image and all.
- **A message part type the thread store does not know is dropped on save.** `normalizePart` in `chat/store.mjs` lists them; a new part type goes there as well as in both `applyEvent`s.
- **`claude -p` cannot ask for permission on its own.** A chat run can (`approve` on `spawnClaudeStream`, chat/approvals.mjs), but only with stdin kept open (steering) and never on a voice turn, a job or a phone request: there a write the prompt asks for is refused unless the bridge allows that path (`allowWrite` → `--allowedTools Edit(…)`), and a small model may still tell the owner it saved. Any new "keep this file updated" rule needs its path added there. A permission request waits on a control response: a new handler for Claude's stdout must answer every `control_request` (an error for subtypes it does not handle) or the CLI hangs.
- **Supervised must name `--permission-mode default`.** Left unset, the account's `~/.claude/settings.json` `defaultMode` decides, and "auto" there turned Supervised into Auto without a word.
- **Codex's sandbox has no network.** `workspace-write` blocks it, so a Codex run that must fetch the web (a totem watching a page) needs `network: true` on `runAgent`, which adds `sandbox_workspace_write.network_access=true`. Without it the run reports a DNS failure rather than erroring.
- **A custom Codex provider loses Codex's hosted tools.** Through a proxy (`model_provider` other
  than `openai`), Codex leaves out image generation and web search unless the provider entry
  sets `requires_openai_auth = true` and `supports_standalone_web_search = true`; it still goes
  through the proxy. Generated images land in `<CODEX_HOME>/generated_images/<session id>/`, not
  in the `--json` stream, so `emitCodexImages` reads that run's folder and shows them in the reply.
- **`codex exec` refuses MCP writes.** Its approval policy is `never`, so any tool without
  `readOnlyHint` fails with "requires approval". `spawnCodexStream` adds
  `default_tools_approval_mode="approve"` for the gateway (`codexGatewayApprovalArgs`), but only
  when `config.toml` defines it and the run is not read-only, because a `-c` override on an
  undefined server stops Codex starting with "invalid transport".
- **The address bar is normalised on boot.** `buildPath` keeps only the query params it knows (`?thread=`/`?project=` on chat, `?totem=` on totems, `?q=` on search, `?chat=` on messages). A new deep-link param must be added there, or anything that reads it after sign-in finds it gone; read one-time params at module load (see `AuthGate.tsx`).
- **`INVOCATION_ID` does not mean "I am the service".** A process started from a shell inside
  any systemd unit (T3 Code's, for one) inherits it. A test bridge that trusted it restarted
  the live `assistant-bridge`. Anything that restarts the unit must first check that
  `systemctl --user show -p MainPID --value <unit>` is its own pid, as `restartBridgeSoon` does.
  On macOS launchd's `XPC_SERVICE_NAME` is inherited the same way; `scripts/service-manager.mjs`
  checks the pid in `launchctl print` before `launchctl kickstart -k`.
- **Apple data needs grants on the node binary, by real path.** Reading `chat.db`, Contacts and
  Photos needs Full Disk Access, and sending needs Automation (node → Messages). Both belong to
  the resolved binary (`/opt/homebrew/Cellar/node@…/bin/node`), so a Homebrew node upgrade drops
  them silently. `GET /api/apple/status` names the path. An ssh session can read these files
  when the service cannot, so test access from a launchd-run process, not from a terminal.
- **Never select a raw date from `chat.db`.** Message dates are nanoseconds since 2001, past
  `Number.MAX_SAFE_INTEGER`, and `node:sqlite` throws a RangeError rather than rounding. Convert
  in SQL (`APPLE_MS` in `apple/messages.mjs`), or bind a BigInt when comparing.
- **An agent never sends a message.** `imessage` proposals are refused by `totem_resolve_inbox`
  even under an approval session (`doResolveInboxItem` checks `approvedVia === 'dashboard'`).
  And "the dashboard" means the approval gate passed, not just the API gate. The bearer
  secret, which agents can read, is refused on `/api/inbox/resolve` and `/api/apple/send` in
  every spelling of the path, and once an approval code is set, sending needs it. Keep it that
  way for any new front door that can accept inbox items, and never route on a path other
  than the normalised one: a handler that trimmed slashes itself once let
  `/api/apple/send/` past a gate that compared the raw path.
- **A route that confers the owner's approval goes in `APPROVAL_ROUTES` first.**
  `bridge.mjs` checks that table (`auth/approval-routes.mjs`) right after the API gate. A
  route left out of it is open to anyone holding `BRIDGE_SECRET`, which is every agent.
  `auth/approval-routes.test.mjs` fails if a second route claims `approvedVia: 'dashboard'`,
  and `auth/approval-bridge.test.mjs` boots the real bridge from a shadow checkout and tries
  every route in the table, in every spelling, with each credential; add the new route's body
  to its `BODIES`.
  A new inbox kind is high risk unless it is added to `LOW_RISK_KINDS`, and it belongs there
  only if an agent could already make the same change through its own tools.
- **An agent never adds an away span.** `away` proposals are refused by `totem_resolve_inbox`
  under an approval session, like `imessage` (`doResolveInboxItem` checks
  `approvedVia === 'dashboard'`), there is no write tool, and agents must not edit
  `data/away.json`. A trip found in an email is an inference: an agent stages it with
  `totem_away_propose`, and the owner accepts it in the dashboard, which is high risk at the
  approval gate (the code once one is set). The owner's own `/api/away` writes are approval
  routes too (a session or the code), so the bearer alone writes no span.
- **An agent never shares a Drive file.** The `drive` scope allows changing permissions, so the
  limit is code: no Drive tool touches the permissions endpoints, and trash is the only delete.
  Keep it that way; a file's contents are untrusted input an agent reads.
- **An agent never acts on LinkedIn.** Its pages are loaded only through `readPage`, whose
  request policy (`browser/read-only.mjs`) aborts every request that is not a GET or HEAD to
  LinkedIn's hosts, so a like, comment, message, read receipt or "seen" ping a page's own script
  tries is never sent. Keep the connector off the chat's interactive browser (`open`, `click`,
  `type`), keep the policy GET-only even when a LinkedIn panel then fails to load, and never add a
  tool that likes, comments, replies, messages, connects or follows: `linkedin__propose_action`
  stages a card the owner does himself. A LinkedIn card's Mark done is his word that he did it, so
  only the dashboard gives it (`approvedVia === 'dashboard'`).
- **An agent never sends an email either.** `gmail.modify` lets the grant send, so the limit is
  code: `gmail.send()` is reachable only from accepting an `email` inbox item, and both its `accept`
  and `draft` actions need `approvedVia === 'dashboard'`, which takes the approval gate: never
  the bearer alone, and the approval code once one is set. What is sent is the reading the
  owner was shown (the dashboard's digest must match), never a second read of the staged
  file. Never add a send tool; email bodies are untrusted input an agent reads.
- **The glow moves every frame, so anything over it is redrawn every frame.** A `backdrop-filter` over it re-blurs on each frame (the chat's full-width veil did, and spun laptop fans), and an animated custom property (`@property`) runs on the main thread, restyling the glow each frame. Keep blur to small surfaces, run the chat's swing phases only while a reply is live (`glow.css`), and apply a `filter` only while it changes something; the composer has no backdrop blur for this reason. The drift pauses while the window is unfocused (`glow-paused` on the root, set in `App.tsx`), during a panel drag (`panel-resizing` on the body) and a window resize (`window-resizing` on the root): its two lights blend (`screen`), and a moving blend over a page changing size was most of a drag's compositor cost. Settings → Chat › Colour glow turns the chat's glow off per device (`chatGlow` in `web/src/settings.ts`, localStorage). The Overview's glass cards take `saturate()` only, no blur, for the same reason (a blur of the already-soft glow changed at most 4/255 per channel).
- **A deploy does not reach a window that is already open.** The desktop app and a pinned tab keep the bundle they loaded, so `web/src/newBuild.ts` polls `/version` (the bundle `web/dist/index.html` names now) and reloads when it changed: at once while hidden, otherwise after two quiet minutes with no unsent text. Active downloads hold that reload even while hidden. Every HTML response, including the SPA fallback for `/chat` and friends, is `cache-control: no-cache`, or a reload brings back the old page.
- **A keystroke must not re-render the thread.** The composer's draft is `ChatView` state, so every keystroke renders the chat view; the messages are behind `chat/MessageLog.tsx`, memoized with memoized rows that take only stable props (ids and the store's actions, never a closure made in `ChatView`), and a streamed token re-renders only the live reply. A new prop on the log must be stable too (`useCallback`, a store value), or typing re-renders every message again, which is what made typing lag in long chats.
- **During a drag or window resize, a reply's text lays out only near the screen.** `.vc-assistant-body > .md` gets `content-visibility: auto` under `body.panel-resizing` and `:root.window-resizing` only (chat.css): a chat column changing width every frame otherwise relaid every message of the thread. Never at rest: WebKit (the macOS app) has no scroll anchoring, so a long chat would jump while scrolling up as skipped replies swap their estimate for their real height. `contain-intrinsic-size: auto` stays on at all times, so each reply's real height is recorded and a skipped one holds exactly that. It clips painting to the text block, so it sits on the text, not the row, whose popovers (reply details, menus) must overflow.
- **A resize handle measures its limits only while in use.** `measure()` sets every panel's variable to 0 and to 100000px to find the limits, three forced layouts of the whole page (the chat reflows at each); it runs on hover (only when the limits are stale), focus, a key or a drag, and on later resizes only while hovered or key-engaged (`engaged` in `ResizeHandle.tsx`; the focus a drag gives the handle does not count). An idle handle carries layout-free bounds, `aria-valuemin` 0 and `aria-valuemax` the window's width, so its `aria-valuenow` is never clamped into 0–100. Measuring on every resize made opening the chats panel and resizing the window pay it for every handle, every frame, and measuring once a resize settles stalled the moment after every drag.
- **The chat's scroll-to-latest arrow follows the dock's height.** Keep `.vc-jump` inside `.vc-dock`, positioned above its top edge. A fixed offset from the chat's bottom overlaps attachments, multiline drafts and the panels above the composer.
- **Desktop file drops use the dashboard's HTML5 handlers.** The main `WebviewWindowBuilder` disables Tauri's native drag/drop handler (`disable_drag_drop_handler`), which otherwise intercepts file drops before the web handlers receive them on Windows. This setting needs a new desktop build, not just a dashboard reload.
- **The chat header folds by measuring, not by width thresholds.** A side panel can leave the chat column any width (down to about 180px), and the header's contents vary, so `chat/headerFold.ts` takes the fewest of its ordered `FOLD_STEPS` that keep the title's floor and writes them to `data-fold` on `.vc-top`; `chat.css` has one rule set per step, and a control marked `data-fold-into="<step>"` moves into "…" (`docs/chat.md` → The header). Never pass `data-fold` as a prop (React would overwrite what the measurement set), keep `titleFloor` continuous in the width (a floor that jumps lets the header unfold as it narrows), and never fold the header with a viewport `@media` rule. A new control in the header needs a `data-fold-into`, a row in `ChatHeader.tsx`'s list and a harness variant (`ChatHeader.harness.tsx`); `scripts/web-layout.test.mjs` renders the real header down to 180px and fails on overlap, a crushed title or a control out of reach. Side panels close on Escape through `usePanelEscape` (`chat/escape.ts`), only when nothing has handled it; anything opening beside them keeps its Escape with `preventDefault` (`useDismiss` does), listening on `document` or its own element, never `window` (the panels' listener there may run first).
- **The page's scrollbar belongs at the shell's edge.** Do not cap the scrolling `.cp-view` itself with `max-width`: wide desktops otherwise show an empty strip beyond its scrollbar. The shell's left chats panel and explicitly opened terminal/canvas keep their own widths; on phones an open terminal is an overlay and must not restore desktop grid columns. `scripts/web-layout.test.mjs` measures the real CSS at desktop and phone widths without a bridge.
- **WKWebView needs a download-start handler.** Without Tauri's `on_download` returning true, macOS cancels the save. Keep its default destination and filename collision handling; only `Finished { success: true }` confirms a native save. Older wrappers cannot report completion and need rebuilding, even after the dashboard reloads. Download activity is portalled to the body so it neither creates a shell grid track nor gets clipped by a preview.
- **An ETag means the phone writes the body to disk.** The iPhone app keeps exactly the answers that carry an ETag, so `ETAG_PATHS` in `http/etag.mjs` is an allow list, not an optimisation: never add a route that streams, changes on every poll (usage meters, anything with a `generatedAt`), reports a run, carries a secret, a token or account settings, answers a typed search, or holds staged mail, messages or journal transcripts (`/api/inbox`, `/api/journal` stay off). A body with a clock in it never 304s: `buildHabitsPayload` dropped its `generatedAt` for this. HTML is outside `/api/` and stays `no-cache` (previous gotcha). Hashing costs about 1 ms per MB of JSON, about a third of the `JSON.stringify` before it. `ETAG_RECORD` tags every `/api/(todos|goals|lists)/<one segment>` as a record, so a new static route there (`/api/todos/issue-states`, live GitHub state) must be excluded in its lookahead or the phone caches it as a task.
- **A popover in the chat that must escape the scroller is portalled to `<body>`.** `.vc-scroll` is a size container (`container: vc-scroll / inline-size`) and on a project's home carries a mask; a `position: fixed` box inside it was placed against the wrong frame (an ancestor walk guessed the container was its containing block, and Chromium disagreed), so the model picker opened shifted by the chats panel and header and clipped. Render it with `createPortal(…, document.body)`, place it with `usePopoverPlacement` (`web/src/chat/ui.tsx`, viewport pixels only), pass the portal's ref to `useDismiss` too, and give it the `--vc-*` colours, since it is outside `.vc`. The Lightbox does the same.
- **A docked panel's width limits are in its CSS, not in JS.** `ResizeHandle` writes width variables and measures what the stylesheet allows (`measure`): a new panel gets its minimum, maximum and the page's minimum as a grid track (`minmax(min, var(--w))`, `shell.css`) or a flex basis with `min-width` (`chat.css`), never an inline `width` or a JS clamp, which gets out of step on the next window resize. The page column's minimum is what the page needs (with a side panel open, the chat's minimum plus the side panel's saved width, `--side-saved`), cut down only by the open panels' minimums (`--main-min`), never a share of the window. Set a width variable on the element that reads it (`.app.shell` for a grid track, the panel for a flex basis) and register it non-inherited (`@property`; `syntax: '*'` with no initial value keeps a `var()` fallback working): an inherited variable, or one changed on the root, restyles everything under it on every frame of a drag. Keep a `var()` fallback equal to the registered initial value, because without `@property` (Safari before 16.4, Firefox before 128) the variable is plain and unset and a fallback-less track lays out as a 538 px rail. A drag or key press is one gesture with one rule: pin every open panel, take from the page then the others in `TAKES_FROM` order, save the dragged panel and each giver's saved width less what it gave, and hold the rest inline until the window's width or the set of open panels changes (`dropHolds`). A hold is the only inline width the handle leaves behind; never add a second width rule beside this one. Work a handle skips mid-drag (measuring its limits, publishing `--term-width`) waits for `PANEL_RESIZE_END`.
- **Never give a scroller `scrollbar-width: thin`.** `styles.css` styles every scrollbar with `::-webkit-scrollbar` (a thin thumb, no track or arrows, which Windows otherwise draws grey down the chat's glow), and Chromium ignores those pseudo-elements on any element whose own `scrollbar-width` or `scrollbar-color` is set. Use `scrollbar-width: none` to hide a bar, or nothing.
